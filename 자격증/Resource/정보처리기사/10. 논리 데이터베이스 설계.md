## 데이터베이스 설계

&emsp;&emsp;

### 정의

- 사용자의 요구를 분석하여 그것들을 컴퓨터에 저장할 수 있는 데이터베이스의 구조에 맞게 변형한 후 특정 DBMS로 데이터베이스를 구현하여 일반 사용자들이 사용하게 하는 것

&emsp;&emsp;

### 데이터베이스 설계 시 고려사항

- 무결성
	- 삽입, 삭제, 갱신 등의 연산 후 에도 데이터베이스에 저장된 데이터가 정해진 제약 조건을 항상 만족해야 한다.
- 일관성
	- 데이터베이스에 저장된 데이터들 사이나, 특정 질의에 대한 응답이 처음부터 끝까지 변함없이 일정해야 함
- 회복
	- 시스템에 장애 발생 시 장애 발생 직전의 상태로 복구 가능해야 함
- 보안
	- 불법적인 데이터의 노출 또는 변경이나 손실로부터 보호 가능해야 함
- 효율성
	- 응답시간의 단축, 시스템의 생산성, 저장 공간의 최적화 등이 가능해야 함
- 데이터베이스 확장성
	- 데이터베이스 운영에 영향을 주지 않으면서 지속적으로 데이터를 추가할 수 있어야 한다.

&emsp;&emsp;

### 데이터베이스 설계 순서 #종종_출제 

1. 요구 조건 분석
	- 요구 조건 명세서 작성
2. 개념적 설계
	- 개념 스키마, 트랜잭션 모델링, E-R 모델
3. 논리적 설계
	- 목표 DBMS에 맞는 논리 스키마 설계, 트랜잭션 인터페이스 설계
4. 물리적 설계
	- 목표 DBMS에 맞는 물리적 구조의 데이터로 변환
5. 구현
	- 목표 DBMS의 DDL로 데이터베이스 생성, 트랜잭션 작성

&emsp;&emsp;

### 요구 조건 분석

- 요구 조건 분석이란, 데이터베이스를 사용할 사람들로부터 필요한 용도를 파악하는 것
- 데이터베이스 사용자에 따른 수행 업무와 필요한 데이터의 종류, 용도, 처리 형태, 흐름, 제약 조건 등을 수집한다.
- 수집된 정보를 바탕으로 요구 조건 명세를 기술한다.

&emsp;&emsp;

### 개념적 설계 #종종_출제 

- 개념적 설계란, 정보의 구조를 얻기 위하여 현실 세계의 무한성과 계속성을 이해하고 다른 사람과 통신하기 위하여 현실 세계에 대한 인식을 추상적 개념으로 표현하는 과정
- 개념적 설계 단계에서는 개념 스키마 모델링과 트랜잭션 모델링을 병행 수행한다.
- 개념적 설계 단계에서는 요구 분석 단계에서 나온 결과인 요구 조건 명세를 DBMS에 독립적인 E-R 다이어그램으로 작성한다.
- DBMS에 독립적인 개념 스키마를 설계한다.

&emsp;&emsp;

### 논리적 설계 #종종_출제 

- 논리적 설계 단계란, 현실 세계에서 발생하는 자료를 컴퓨터가 이해하고 처리할 수 있는 물리적 저장장치에 저장할 수 있도록 변환하기 위해 특정 DBMS가 지원하는 논리적 자료 구조로 변환시키는 과정
- 개념 세계의 데이터를 필드로 기술된 데이터 타입과 이 데이터 타입들 간의 관계로 표현되는 논리적 구조의 데이터로 모델화 한다.
- 개념적 설계가 개념 스키마를 설계하는 단계라면 논리적 설계에서는 개념 스키마를 평가 및 정제하고 DBMS에 따라 서로 다른 논리적 스키마를 설계하는 단계이다.
- 트랜잭션의 인터페이스를 설계한다.
- 관계형 데이터베이스라면 테이블을 설계하는 단계이다.

&emsp;&emsp;

### 물리적 설계 #매우_자주_출제 

- 물리적 설계란, 논리적 설계 단계에서 논리적 구조로 표현된 데이터를 디스크 등의 물리적 저장장치에 저장할 수 있는 물리적 구조의 데이터로 변환하는 과정
- 물리적 설계 단계에서는 다양한 데이터베이스 응용에 대해 처리 성능을 얻기 위해 데이터베이스 파일의 저장 구조 및 액세스 경로를 결정한다.
- 저장 레코드의 양식, 순서, 접근 경로, 조회가 집중되는 레코드와 같은 정보를 사용하여 데이터가 컴퓨터에 저장되는 방법을 묘사

#### 물리적 설계시 고려 사항

- 트랜잭션 처리량, 응답 시간, 디스크 용량, 저장공간의 효율화

&emsp;&emsp;

### 구현

- 데이터베이스 구현 단계란, 논리적 설계 단계와 물리적 설계 단계에서 도출된 데이터 스키마를 파일로 생성하는 과정
- 사용하려는 특정 DBMS의 DDL을 이용하여 데이터베이스 스키마를 기술한 후 컴파일하여 빈 데이터베이스 파일을 생성한다.
- 생성된 빈 데이터베이스 파일에 데이터를 입력한다.
- 응용 프로그램을 위한 트랜잭션을 작성한다.
- 데이터베이스 접근을 위한 응용 프로그램을 작성한다.

## 데이터 모델의 개념

&emsp;&emsp;

### 정의

- 데이터 모델이란, 현실 세계의 정보들을 컴퓨터에 표현하기 위해 단순화, 추상화하여 체계적으로 표현한 개념적 모형
- 데이터 모델은 데이터, 데이터의 관계, 데이터의 의미 및 일관성, 제약 조건 등을 기술하기 위한 개념적 도구들의 모임
- 데이터베이스 설계 과정에서 데이터의 구조를 논리적으로 표현하기 위해 사용되는 지능적 도구로 현실 세계를 데이터베이스에 표현하는 중간 과정이다.

&emsp;&emsp;

### 데이터 모델의 구성 요소

- 개체
	- 데이터베이스에 표현하려는 것으로 사람이 생각하는 개념이나 정보 단위 같은 현실 세계의 대상체
- 속성
	- 데이터의 가장 작은 논리적 단위로서 파일 구조상의 데이터 항목 또는 데이터 필드에 해당
- 관계
	- 개체 간의 관계 또는 속성 간의 논리적인 연결을 의미

#### 관계의 형태 #가끔_출제 

- 일 대 일
	- 개체 집합 A의 각 원소가 개체 집합 B의 원소 한 개와 대응하는 개체
- 일 대 다
	- 개체 집합 A의 각 원소가 개체 집합 B의 원소 여러 개와 대응하고 있지만, 개체 집합 B의 각 원소는 개체 집합 A의 원소 한개와 대응하는 관계
- 다 대 다
	- 개체 집합 A의 각 원소가 개체 집합 B의 원소 여러 개와 대응하고 있고, 개체 집합 B의 각 원소는 개체 집합 A의 원소 여러 개와 대응하는 관계

&emsp;&emsp;

### 개념적 데이터 모델

- 개념적 데이터 모델이란, 현실 세계에 대한 인간의 이해를 돕기 위해 현실 세계에 대한 인식을 추상적 개념으로 표현하는 과정
- 개념적 데이터 모델은 속성들로 기술된 개체 타입과 이 개체 타입들 간의 관계를 이용하여 현실 세계를 표현한다.
- 개념적 데이터 모델은 현실 세계에 존재하는 개체를 인간이 이해할 수 있는 정보 구조로 표현하기 때문에 정보 모델이라고도 한다.
- 대표적인 개념적 데이터 모델로는 E-R 모델

&emsp;&emsp;

### 논리적 데이터 모델

- 논리적 데이터 모델이란, 개념적 모델링 과정에서 얻은 개념적 구조를 컴퓨터가 이해하고 처리할 수 있는 컴퓨터 세계의 환경에 맞도록 변환하는 과정
- 논리적 데이터 모델은 필드로 기술된 데이터 타입과 이 데이터 타입들 간의 관계를 이용하여 현실 세계를 표현한다.
- 단순히 데이터 모델이라고 하면 논리적 데이터 모델을 의미한다.
- 특정 DBMS는 특정 논리적 데이터 모델 하나만 선정하여 사용한다.
- 논리적 데이터 모델은 데이터 간의 관계를 어떻게 표현하느냐에 따라 관계 모델, 계층 모델, 네트워크 모델로 구분한다.

&emsp;&emsp;

### 데이터 모델에 표시할 요소 #자주_출제 

- 구조
	- 논리적으로 표현된 개체 타입들 간의 관계로서 데이터 구조 및 정적 성질을 표현한다.
- 연산
	- 데이터베이스에 저장된 실제 데이터를 처리하는 작업에 대한 명세
	- 데이터베이스를 조작하는 기본 도구
- 제약 조건
	- 데이터베이스에 저장될 수 있는 실제 데이터의 논리적인 제약 조건

## E-R 모델

&emsp;&emsp;

### 개요 #가끔_출제 

- E-R 모델이란, 개념적 데이터 모델의 가장 대표적인 모델이며 1976년 피터 첸에 의해 제안되고 기본적인 구성 요소가 정립되었다.
- E-R 모델은 개체와 개체 간의 관계를 기본 요소를 이용하여 현실 세계의 무질서한 데이터를 개념적인 논리 데이터로 표현하기 위한 방법으로 많이 사용중이다.
- E-R 모델은 개체 타입은 이들 간의 관계 타입을 이용해 현실 세계를 개념적으로 표현한다.
- E-R 모델에서는 데이터를 개체, 관계, 속성으로 묘사한다.
- E-R 모델은 특정 DBMS를 고려한 것이 아니다.
- E-R 다이어그램으로 표현하며 1:1, 1:N, N:M 등의 관계 유형을 제한 없이 나타낼 수 있다.
- 최초에는 개체, 관계, 속성과 같은 개념들로 구성되었으나 나중에는 일반화 계층 같은 복잡한 개념들이 첨가되어 확장된 모델로 발전했다.

&emsp;&emsp;

### E-R 다이어그램 #매우_자주_출제 

- E-R 다이어그램이란, E-R 모델의 기본 아이디어를 시각적으로 표현하기 위한 그림이다.
- 실체 간의 관계는 물론 조직, 사용자, 프로그램, 데이터 등 시스템 내에서 역할을 가진 모든 실체를 표현한다.

#### E-R 다이어그램 구성 요소

- 사각형 #자주_출제 
	- 개체 타입
- 마름모 #자주_출제 
	- 관계 타입
- 타원 #매우_자주_출제 
	- 속성
- 이중타원 #아주_가끔_출제 
	- 다중값 속성(복합 속성)
- 밑줄타원
	- 기본키 속성
- 복수 타원
	- 복합 속성
- 관계
	- 1:1, 1:N, N:M 등의 개체 간 관계에 대한 대응수를 선 위에 기술함
- 선, 링크 #자주_출제 
	- 개체 타입과 속성을 연결

#### E-R 다이어그램 대응수

- 대응수는 함수 관계도를 이용해 쉽게 구할 수 있다.

## 관계형 데이터베이스의 구조

&emsp;&emsp;

### 개요

- 1970년 IBM에 근무하던 코드에 의해 처음 제안
- 관계형 데이터베이스를 구성하는 개체나 관계를 모두 릴레이션이라는 표로 표현
- 릴레이션은 개체를 표현하는 개체 릴레이션, 관계를 나타내는 관계 릴레이션으로 구분할 수 있다.

#### 장단점

- 장점
	- 간결하고 보기 편리함
	- 다른 데이터베이스로의 변환이 용이함
		- 이건 이상한 소리임, 테이블 특성에 따라 변환이 난해한 경우가 많음
- 단점
	- 성능이 다소 떨어짐
		- 이건 이상한 소리임, 성능은 설계에 따라 달라짐

&emsp;&emsp;

### Relation 구조 #매우_자주_출제 

- 릴레이션이란, 데이터들을 표 형태로 표현한 것으로 구조를 나타내는 릴레이션 스키마와 실제 값들인 릴레이션 인스턴스로 구성된다.

#### 튜플

- 튜플이란 릴레이션을 구성하는 각각의 행을 의미한다.
- 튜플은 속성의 모임으로 구성된다.
- 파일 구조에서 레코드와 같은 의미
- 튜플의 수를 카디널리티 또는 기수, 대응수라고 한다.

#### 속성

- 속성은 데이터베이스를 구성하는 가장 작은 논리적 단위이다.
- 파일 구조상의 데이터 항목 또는 데이터 필드에 해당된다.
- 속성은 개체의 특성을 기술한다.
- 속성의 수를 디그리 또는 차수라고 한다.

#### 도메인

- 도메인은 하나의 애트리뷰트가 취할 수 있는 같은 타임의 원자값들의 집합이다.
- 도메인은 실제 속성(애트리뷰트) 값이 나타날 때 그 값의 합법 여부를 시스템이 검사하는데에도 이용된다.

&emsp;&emsp;

### 릴레이션의 특징 #자주_출제 

- 한 릴레이션에는 똑같은 튜플이 포함될 수 없으므로 릴레이션에 포함된 튜플들은 모두 상이하다.
- 한 릴레이션에 포함된 튜플 사이에는 순서가 없다.
- 튜플들의 삽입, 삭제 등의 작업으로 인해 릴레이션은 시간에 따라 변한다.
- 릴레이션 스키마를 구성하는 속성들 간의 순서는 중요하지 않다.
- 속성의 유일한 식별을 위해 속성의 명칭은 유일해야 하지만, 속성을 구성하는 값은 동일한 값이 있을 수 있다.
- 릴레이션을 구성하는 튜플을 유일하게 식별하기 위해 속성들을 부분집합을 키로 설정한다.
- 속성의 값은 논리적으로 더 이상 쪼갤 수 없는 원자값만을 저장한다.

<br><br><br>

## 관계형 데이터베이스의 제약 조건 - 키

&emsp;&emsp;

- 제약 조건이란, 데이터베이스에 저장되는 데이터의 정확성을 보장하기 위하여 키를 이용하여 입력되는 데이터에 제한을 주는 것으로 개체 무결성 제약, 참조 무결성 제약 등이 포함된다.

&emsp;&emsp;

### 키의 개념

- 키란, 데이터베이스에서 조건을 만족하는 튜플을 찾거나 순서대로 정렬할 때 튜플들을 서로 구분할 수 있는 기준이 되는 애트리뷰트를 말함

&emsp;&emsp;

### 후보키 #종종_출제 

- 후보키란, 릴레이션을 구성하는 속성들 중에서 튜플을 유일하기 식별하기 위해 사용하는 속성들의 부분집합이다.
	- 기본키로 사용 가능한 속성을 의미한다.
- 하나의 릴레이션 내에서는 중복된 튜플들이 있을 수 없으므로 모든 릴레이션에는 반드시 하나 이상의 후보키가 존재한다.
- 후보키는 릴레이션에 있는 모든 튜플에 대해 동시에 유일성과 최소성을 만족한다.
	- 예로 들면 학생 릴레이션의 학번이나 주민번호가 대표적인 후보키이다.

#### 후보키의 특성

- 유일성
	- 하나의 키 값으로 하나의 튜플만을 유일하게 식별할 수 있어야 한다.
- 최소성
	- 모든 레코드들을 유일하게 식별하는 데 꼭 필요한 속성으로만 구성되어야 한다.

&emsp;&emsp;

### 기본키 #가끔_출제 

- 기본키란, 후보키 중에서 특별히 선정된 주 키로 중복된 값을 가질 수 없다.
- 한 릴레이션에서 특정 튜플을 유일하게 구별할 수 있는 속성이다.
- 기본키는 유일성과 최소성을 가지며 튜플을 식별하기 위해서는 반드시 필요한 키이다.
- 기본키는 NOT NULL로써 NULL이 들어올 수 없다.


&emsp;&emsp;

### 대체키

- 대체키란, 후보키가 둘 이상일 때 기본키를 제외한 나머지 후보키들을 의미한다.

&emsp;&emsp;

### 슈퍼키 #자주_출제 

- 슈퍼키란, 한 릴레이션 내에 있는 속성들의 집합으로 구성된 키이며 릴레이션을 구성하는 모든 튜플들 중 슈퍼키로 구성된 속성의 집합과 동일한 값은 나타나지 않는다.
- 슈퍼키는 릴레이션을 구성하는 모든 튜플에 대해서 유일성은 만족하지만 최소성을 만족시키지 못한다.
	- 예로 들면 학생 릴레이션에서 학번, 주번, '학번 + 주번', '주번+성명', '학번+주번+성명' 등으로 구성이 가능하다.

&emsp;&emsp;

### 외래키 #자주_출제 

- 외래키란, 다른 릴레이션의 기본키를 참조하는 속성 또는 속성들의 집합이다.
- 외래키는 참조되는 릴레이션의 기본키와 대응되어 릴레이션 간의 참조 관계를 표현하는데 중요한 도구가 된다.
- 한 릴레이션에 속한 속성 A와 참조 릴레이션의 기본키인 B가 동일한 도메인 상에서 정의되었을 때의 속성 A를 외래키라 한다.
- 외래키로 지정되면 참조 릴레이션의 기본키에 없는 값은 입력 불가능하다.


<br><br><br>

## 관계형 데이터베이스의 제약 조건 - 무결성

&emsp;&emsp;

### 무결성 개념

- 무결성이란, 데이터베이스에 저장된 데이터 값과 그것이 표현하는 현실 세계의 실제 값이 일치하는 정확성을 의미한다.
- 무결성 제약 조건은 데이터베이스에 들어있는 데이터의 정확성을 보장하기 위해 부정확한 자료가 데이터베이스 내에 저장되는 것을 방지하기 위한 제약 조건을 말한다.
- 무결성의 종류는 개체, 도메인, 참조, 사용자 정의 무결성 등이 존재한다.

&emsp;&emsp;

### 개체 무결성 #매우_자주_출제 

- 개체 무결성이란, 기본 테이블의 기본키를 구성하는 어떤 속성도 NULL값이나 중복값을 가질 수 없다는 규정이다.
	- PK를 걸면 기본적으로 지키기 싫어도 지켜지는 속성이다.

&emsp;&emsp;

### 도메인 무결성 #종종_출제 

- 도메인 무결성이란, 주어진 속성 값이 정의된 도메인에 속한 값이여야 한다.
	- 예를 들면, 0~100까지의 점수가 들어와야하는 점수 칸에 나이가 들어간다던지 하는 무결성이다.
	- 이건 따로 DB 레이어가 아닌 애플리케이션 레이어에 철저히 계약된 기능 요구사항대로 정의되어야한다.
		- 보통 DB 레이어에 구현가능한 기능 요구사항도 존재하긴하는데 보통 기타 트랜잭션 로직들이 그에 해당된다.
			- 사용자 등급 이벤트나 프로모션 이런 것들이 대표적이다.

&emsp;&emsp;

### 참조 무결성 #종종_출제 

- 참조 무결성이란, 외래키 값은 NULL이거나 참조 릴레이션의 기본키 값과 동일해야한다는 규정이다.
	- 다만, 이것은 개인적으로 생각하기에 설계에 따라 좀 애매할 수 있다고 생각한다.
		- 테이블에 일시적으로 생성해둬야하는 경우에는 일시적으로 NULLABLE 할 수도 있다고 생각한다.
		- 다만, 참조 무결성에 따르면 이는 허용되선 안되지만 설계상 허용 되게끔도 만들 수 있다는 의미이다.
- 외래키와 참조하려는 테이블의 기본키는 도메인과 속성 개수가 일치해야 한다.

&emsp;&emsp;

###  사용자 정의 무결성 #아주_가끔_출제 

- 사용자 정의 무결성이란, 속성 값들이 사용자가 정의한 제약조건에 만족해야한다는 규정이다.

&emsp;&emsp;

###  데이터 무결성 강화

- 데이터 무결성은 데이터 품질에 직접적인 영향을 끼치므로 데이터 특성에 맞는 적절한 무결성을 정의하고 강화해야 한다.
- 프로그램이 완성되고 데이터가 저장된 상태에서 무결성을 정의할 경우 많은 비용이 발생하므로 데이터베이스 구축 과정에서 정의한다.
	- 이게 말이 쉽지 실제로는 어렵기 때문에 Flyway같은 라이브러리를 이용하여 마이그레이션 하는 것이 오늘날 가장 보편적인 백엔드 애플리케이션 설계 및 구축 과정이라고 생각한다.
- 데이터 무결성은 애플리케이션, 데이터베이스 트리거, 제약 조건을 이용하여 강화할 수 있다.

#### 무결성 도구 종류

- 애플리케이션
	- 설명
		- 데이터 생성, 수정, 삭제 시 무결성 조건을 검증하는 코드를 데이터를 조작하는 프로그램 내에 추가한다.
		- 코드를 이용한 복잡한 규칙 등을 검토하는 무결성 검사는 데이터베이스에서 수행하기 어려우므로 애플리케이션 내에서 처리한다.
	- 장점
		- 사용자 정의 같은 복잡한 무결성 조건의 구현이 가능하다.
	- 단점
		- 소스 코드에 분산되어 관리가 힘들다
		- 개별적인 시행으로 인해 적정성 검토가 어렵다.
			- 이것 때문에 데이터 사용자 정의 요구사항들은 죄다 테스트 코드로 만들어둬야 한번에 적정성 검토가 가능해지기 때문에 여기에서 테스트 코드의 진가가 들어난다.
			- 괜히 과거에 TDD가 유행했던게 아니다.
- 데이터베이스 트리거
	- 설명
		- 트리거 이벤트에 무결성 조건을 실행하는 절차형 SQL을 추가한다.
	- 장점
		- 통합 관리가 가능하다.
		- 복잡한 요구 조건의 구현이 가능하다.
	- 단점
		- 서비스 운영 중 변경이 어렵다.
		- 사용상 주의가 필요하다.
		- DB에 의존적인 구현이므로 데이터베이스 이관에 난해성을 더한다.
			- 이 문제로 인해 오늘날에는 왠만해선 애플리케이션에 모든 무결성 조건을 추가한다.
- 제약 조건
	- 설명
		- 데이터베이스에 제약 조건을 설정하여 무결성을 유지한다.
	- 장점
		- 통합 관리 가능하다.
		- 간단한 선언으로 구현이 가능하다.
		- 변경이 용이하다.
		- 오류 데이터 발생 방지 등이 있다.
	- 단점
		- 복잡한 제약 조건의 구현과 예외적인 처리가 불가능하다.
			- 이로 인해 실무에서는 애플리케이션과 제약 조건만을 두는 편이다.

<br><br><br>

## 관계대수 및 관계해석

&emsp;&emsp;

### 관계대수의 개요 #매우_자주_출제 

- 관계대수란, 관계형 데이터베이스에서 원하는 정보와 그 정보를 검색하기 위해서 어떻게 유도하는가를 기술하는 절차적 언어이다.
	- 관계대수는 매우 중요한 연산으로 실무에서 실행되는 연산 중 70~90프로에 해당하는 연산이 관계대수이다.
	- 관계대수는 그대로 연산되는 것이 아닌, 옵티마이저에 의해 해석된 뒤 수식을 옵티마이저가 만들어 수행한다.
		- 즉, 옵티마이저의 동작 우선 순위등을 이해해야 효과적으로 튜닝이 가능하다.
		- 일종의 컴파일러나 인터프리터의 역할이라고 보면 편하다.
- 관계대수는 릴레이션을 처리하기 위해 연산자와 연산규칙을 제공하는 언어로 피연산자가 릴레이션이고 결과도 릴레이션이다.
- 질의에 대한 해를 구하기 위해 수행해야 할 연산의 순서를 명시한다.
- 관계대수에는 관계 데이터베이스에 적용하기 위해 특별히 개발한 순수 관계 연산자와 수학적 집합 이론에서 사용하는 일반 집합 연산자가 있다.

#### 관계대수 종류

- 순수 관계 연산자
	- Select, Project, Join, Division
- 일반 집합 연산자
	- UNION(합집합), INTERSECTION(교집합), DIFFERENCE(차집합), CARTESIAN PRODUCT(교차곱)
		- 유니온과 카타시안은 실무에서 왠만해선 지양하는 연산이다.

&emsp;&emsp;

### Select #자주_출제 

- Select란, 릴레이션에 존재하는 튜플 중에서 선택 조건을 만족하는 튜플의 부분집합을 구해 새로운 릴레이션을 만드는 연산이다.
- 릴레이션의 행에 해당하는 튜플을 구하는 것이므로 수평 연산이라고도 부른다.
- 연산자의 기호은 그리스 문자 시그마(σ)를 사용한다.

#### 표기 형식

- σ<조건>(R)
	- R은 릴레이션 이름이다.
	- 조건 안에는 =, !=, <, <=, >, >= 등의 기호를 이용한 비교 연산이 허용된다.
		- AND, OR, NOT 등의 논리 연산자를 사용해 여러개의 조건을 하나로 만들 수 있다.

&emsp;&emsp;

### Project

- Project란, 주어진 릴레이션에서 속성 리스트에 제시된 속성 값만을 추출하여 새로운 릴레이션을 만드는 연산
	- 단, 연산 결과에 중복 발생시 중복이 제거된다.
- 릴레이션의 열에 해당하는 속성을 추출하는 것이므로 수직 연산자라고도 부른다.
- 연산자의 기호는 그리스 문자 파이(𝛑)

#### 표기 형식

- 𝛑<속성리스트>(R)

&emsp;&emsp;

### Join

- Join이란, 공통 속성을 중심으로 두 개의 릴레이션을 하나로 합쳐서 새로운 릴레이션을 만드는 연산이다.
- Join의 결과로 만들어진 릴레이션의 차수는 조인된 두 릴레이션의 차수를 합한 것과 같다.
- Join의 결과는 교차곱을 수행한 뒤 Select를 수행한 것과 같다.
- 연산자 기호는 ⨝을 사용한다.

#### 표기 형식

- R $⨝_{키속성r=키속성s}$ S
	- 키속성 r은 릴레이션 R의 속성, 키속성 s는 릴레이션 S의 속성이다.


#### 자연 조인

- 조인 조건이 = 일 때, 동일한 속성이 두 번 나타나게 되는데 이중 중복된 속성을 제거하여 같은 속성을 한 번 만 표기하는 방법을 자연 조인이라고 한다.
- 자연 조인의 성립을 원한다면 두 릴레이션의 속성명과 도메인이 같아야한다.
	- 예시에서는 두 릴레이션의 한 속성이 이름이 같아서 R $⨝_{키속성r=키속성s}$ S 이렇게 안하고 R $⨝_{키속성r}$ S 이렇게 적고 자연 조인임을 나타냈다.

&emsp;&emsp;

### Division #종종_출제 

- Division이란, X⊃Y인 두 개의 릴레이션 R(X)와 S(Y)가 있을 때, R의 속성이 S의 속성 값을 모두 가진 튜플에서 S가 가진 속성을 ==**제외한 속성만을 구하는 연산**==
	- 제외한 속성만을 구하므로 적혀있는 속성을 제외한 나머지가 조회되게 된다.
- 연산 기호는 ÷를 사용한다.

#### 표기 형식

- R$[속성r ÷ 속성s]$S
	- 속성 r은 릴레이션 R의 속성, 속성 s는 릴레이션 S의 속성
	- 속성 r과 속성 s는 동일 속성값을 가지는 속성이여야 한다.

&emsp;&emsp;

### 일반 집합 연산자 #매우_자주_출제 

- 일반 집합 연산자란, 수학적 집합 이론에서 사용하는 연산자로서 릴레이션 연산에도 그대로 적용 가능하다.
- 일반 집합 연산자 중 합집합, 교집합, 차집합을 처리하기 위해서는 합병 조건을 만족해야한다.

#### 합병 가능한 두 릴레이션이 R, S가 있을 때 각 연산의 특징

- 합집합, Union ∪
	- 기능 및 수학적 표현
		- 두 릴레이션에 존재하는 튜플의 합집합을 구하되, 결과로 생성된 릴레이션에서 중복되는 튜플은 제거되는 연산
		- R ∪ S = {t | t ∈ R ⋁ t ∈ S }
		- t는 릴레이션 R 또는 S에 존재하는 튜플이다.
	- 카디널리티
		- |R ∪ S| <= |R| + |S|
		- 합집합의 카디널리티는 두 릴레이션 카디널리티의 합보다 크지 않다.
- 교집합, Intersection ⋂
	- 기능 및 수학적 표현
		- 두 릴레이션에 존재하는 튜플의 교집합을 구하는 연산이다.
		- R ∪ S = {t | t ∈ R ⋀ t ∈ S }
		- t는 릴레이션 R 그리고 S에 동시에 존재하는 튜플이다.
		- 일반적으로 `left join ... on` 조건을 걸면 교집합 결과가 나온다
	- 카디널리티
		- |R ⋂ S| <= MIN{|R|, |S|}
		- 교집합의 카디널리티는 두 릴레이션 중 카디널리티가 적은 릴레이션의 카디널리티보다 크지 않다.
- 차집합, Difference -
	- 기능 및 수학적 표현
		- 두 릴레이션에 존재하는 튜플의 차집합을 구하는 연산
		- R - S = {t | t ∈ R ⋀ t  ∉ S }
		- t는 릴레이션 R에는 존재하고 S에 없는 튜플이다.
	- 카디널리티
		- |R - S| <= |R|
		- 차집합의 카디널리티는 릴레이션 R의 카디널리티 보다 크지 않다.
- 교차곱, Cartesian Product ⨯
	- 기능 및 수학적 표현
		- 두 릴레이션에 있는 튜플들의 순서 쌍을 구하는 연산
		- R ⨯ S = {r · s | r ∈ R ⋀ s ∈ S }
	- 카디널리티
		- |R ⨯ S| = |R| ⨯ |S|
		- 교차곱의 디그리는 두 릴레이션의 디그리를 더한 것과 같고, 카디널리티는 두 릴레이션의 카디널리티를 곱한 것과 같다.

### 관계해석 #자주_출제 

- 관계해석은 관계 데이터 모델의 제안자인 코드가 수학의 술어 해석(Predicate Calculus)에 기반을 두고 관계 데이터베이스를 위해 제안함
- 관계해석은 관계 데이터 연산을 표현하는 방법이며 원하는 정보를 정의할 때는 계산 수식을 사용한다.
- 관계해석은 원하는 정보가 무엇이라는 것만 정의하는 비절차적 특성을 지닌다.
- 튜플 관계해석과 도메인 관계해석이 있다.
- 기본적으로 관계해석과 관계대수는 관계 데이터베이스를 처리하는 기능과 능력면에서 동등하며, 관계대수로 표현한 식은 관계해석으로 표현할 수 있다.
- 질의어로 표현한다.

#### 주요 논리 기호

- ∀
	- 전칭 전량자
	- 가능한 모든 튜플에 대하여
- ∃
	- 존재 전량자
	- 하나라도 일치하는 튜플이 있음

## 정규화

&emsp;&emsp;

### 개요 #자주_출제 

- 정규화란, 함수적 종속성 등의 종속성 이론을 이용하여 잘못 설계된 관계형 스키마를 더 작은 속성의 세트로 쪼개 바람직한 스키마로 만들어 가는 과정
- 하나의 종속성이 하나의 릴레이션에 표현될 수 있도록 분해해가는 과정이라 할 수 있음
- 정규형에는 제1정규형, 제2정규형, 제3정규형, BCNF형, 제4정규형, 제5정규형이 있다.
	- 차수가 높아질수록 만족시켜야 할 제약 조건이 늘어난다.
- 정규화는 데이터베이스 논리적 설계 단게에서 수행한다.
- 정규화는 논리적 처리 및 품질에 큰 영향을 미친다.
- 정규화된 데이터 모델은 일관성, 정확성, 단순성, 비중복성, 안정성 등을 보장한다.
- 정규화 수준이 높을수록 유연한 데이터 구축이 가능하고 데이터의 정확성이 높아지지만 물리적 접근이 복잡하고 너무 많은 조인으로 인해 조회 성능이 하락한다.
	- 실제 실무에서는 대부분 제 3 정규형 정도에서 만족한다.

&emsp;&emsp;

### 목적 #종종_출제 

- 데이터 구조의 안정성 및 무결성 유지
- 어떠한 릴레이션이라도 데이터베이스 내에서 표현 가능
- 효과적인 검색 알고리즘 생성 가능
- 데이터 중복을 배제하여 이상의 발생 방지 및 자료 저장 공간의 최소화
- 데이터 삽입 시 릴레이션을 재구성할 필요성을 줄임
- 데이터 모형의 단순화가 가능
- 속성의 배열 상태 검증 가능
- 개체와 속성의 누락 여부 확인 가능
- 자료 검색과 추출의 효율성 증대

&emsp;&emsp;

### 이상의 개념 및 종류 #매우_자주_출제 

- 이상이란, 정규화를 거치지 않아 데이터베이스 내애 데이터들이 불필요하게 중복되어 릴레이션 조작 시 발생되는 예기치 못한 곤란한 현상

#### 종류

- 삽입 이상
	- 릴레이션에 데이터 삽입 시 의도와 상관없이 원하지 않은 값들도 함께 삽입되는 현상
- 삭제 이상
	- 릴레이션에서 한 튜플을 삭제할 때 의도와는 상관없는 값들도 함께 삭제되는 연쇄가 일어나는 현상
- 갱신 이상
	- 릴레이션에서 튜플에 있는 속성값을 갱신할 시 일부 튜플의 정보만 갱신되어 정보에 모순이 생기는 현상

&emsp;&emsp;

### 원칙

- 하나의 스키마를 다른 스키마로 변환 시 정보의 손실이 있어서는 안되며 이를 정보의 무손실 표현이라 한다.
- 하나의 독립된 관계성은 하나의 독립된 릴레이션으로 분리시켜 표현해야하며 이를 분리의 원칙이라 한다.
- 데이터의 중복성이 감소되어야 한다.

&emsp;&emsp;

### 정규화 과정 #매우_자주_출제 #매우_자주_출제 

- 1NF
	- 릴레이션에 속한 모든 도메인이 원자값으로만 되어 있는 정규형
	- 릴레이션의 모든 속성이 단순 영역에서 정의된다.
		- 단, 단순 로깅용 데이터를 넣는 다는 명목하에 이 정규형을 깨는 패턴도 존재한다.
		- JSONB를 활용한 패턴이 대표적이다.
- 2NF
	- 릴레이션 R이 1NF일 때, 기본키가 아닌 모든 속성이 기본키에 대하여 완전 함수적 종속을 만족하는 정규형
		- 다른 테이블에 해당하는 속성 연관된 다른 기본키까지 포함된 속성을 한 튜플에 존재한다면 그건 더 뜯어 내야한다는 의미
		- 단, 특수한 성능 문제가 존재하는 경우에 조인을 덜하기 위해 완전 함수적 종속을 피할 수도 있다.
- 3NF
	- 릴레이션 R이 2NF이고, 기본키가 아닌 모든 속성이 기본키에 대해 이행적 종속을 만족하지 않는 정규형
	- 무손실 조인 또는 종속성 보존을 저해하지 않고도 항상 3NF 설계를 얻을 수 있다.
- BCNF
	- 릴레이션 R에서 결정자가 모두 후보키인 정규형
	- 3NF에서 후보키가 여러 개 존재하고 서로 중첩되는 경우에 적용하는 강한 제3정규형이라고도 부른다.
	- 모든 BCNF가 종속성을 보존하는 것은 아니다.
	- 제약조건은 다음과 같다.
		- 키가 아닌 모든 속성은 각 키에 대하여 완전 종속해야 한다.
		- 키가 아닌 모든 속성은 그 자신이 부분적으로 들어가 있지 않은 모든 키에 대하여 완전 종속해야 한다.
		- 어떤 속성도 키가 아닌 속성에 대해서는 완전 종속할 수 없다.
- 4NF
	- 릴레이션 R이 다치 종속 A -> B가 성립하는 경우 R의 모든 속성이 A에 함수적 종속 관계를 만족하는 정규형
- 5NF
	- 릴레이션 R의 모든 조인 종속이 R의 후보키를 통해서만 성립되는 정규형

#### 함수적 종속 / 완전 / 부분 함수적 종속 및 이해

- 함수적 종속
	- 데이터들이 어떤 기준값에 의해 종속되는것
	- 예를 들어 수강 릴레이션이 학번 이름 과목명으로 되어 있는 경우 학번이 결정되면 과목명에 상관없이 학번에는 항상 이름이 대응된다.
		- 이처럼 학번에 따라 이름이 결정 될 때 "이름이 학번에 함수 종속적이다"라고 한다.
- 완전 함수적 종속
	- 어떤 테이블 R에서 속성 A가 다른 속성 집합 B 전체에 대해 함수적 종속이지만 속성 집합 B의 어떠한 진부분집합 C에는 함수적 종속이 아닐 때, 속성 A는 속성 집합 B에 완전 함수적 종속이라고 함
	- 풀어서 설명하자면, 속성 A가 여러 개의 속성으로 구성된 B에 의해 결정되는 속성이고, B의 일부인 여러 개의 속성들인 C로는 속성 A가 결정되지 않을 때, 속성 A가 속성 집합 B에 완전 함수적 종속이라는 뜻
- 부분 함수적 종속
	- 어떤 테이블 R에서 속성 A가 다른 속성 집합 B 전체에 대해 함수적 종속이면서 속성 집합 B의 어떠한 진부분 집합에도 함수적 종속일 때, 속성 A는 속성 집합 B에 부분 함수적 종속이라고 함.
- 완전/부분 함수적 종속의 이해
	- 예를 들면 성적 테이블의 경우,  학번, 과목번호, 성적으로 구성되있다고 가정할 때, 속성집합 B는 학번과 과목 번호이며, 이때 진부분집합 C는 학번이거나 과목 번호인 것이다. 성적은 학번에 의해 결정될 수 없고 과목 번호에 의해 결정될 수 없음, 성적은 오로지 학번과 과목번호가 함께 있을 때 결정되는 속성임
		- 이때 성적은 학번과 과목번호에 완전 함수적 종속이라고 함
	- 위의 완전 함수적 종속 예시에서 만약 이름과 과목명이 추가된 경우, 이름은 학번에만 종속적이므로 학번에 부분 함수적 종속이라고 부르고 과목명은 과목 번호에만 종속적이므로 과목 번호에 부분 함수적 종속이라고 부른다.

#### 정규화 과정 정리

-  두부이걸다조? => ==**도부이결다조**== 를 외워두자.

1. 비정규 릴레이션
	- 여기에서 도메인이 원자값이면 1NF
2. 1NF
	- 여기에서 부분적 함수 종속을 제거하면 2NF
3. 2NF
	- 여기에서 이행적 함수 종속을 제거하면 3NF
4. 3NF
	- 여기에서 결정자이면서 후보키가 아닌 것을 제거하면 BCNF
5. BCNF
	- 여기에서 다치 종속을 제거하면 BCNF
6. 4NF
	- 여기에서 조인 종속을 제거하면 5NF
7. 5NF

## 반정규화

&emsp;&emsp;

### 개요 #자주_출제 

- 반정규화란, 시스템의 성능 향상, 개발 및 운영의 편의성 등을 위해 정규화된 데이터를 통합, 중복, 분리하는 과정이다.
	- 의도적으로 정규화 원칙을 위배하는 것이다.
	- 실무 초반에는 의도적으로 정규화를 4차까지 진행하고 역정규화를 하는 것을 권장하며 짬이 좀 쌓이게 되면 서비스의 특성만 보고서도 바로 역정규화된 테이블로 알아서 뇌에서 구성하게 된다.
- 반정규화를 수행하면 시스템의 성능이 향상되고 관리 효율성은 증대하지만 데이터의 일관성 및 정합성이 저하될 수 있다.
	- 오늘날 mongoDB가 핫한 이유는 이런 일관성과 정합성을 제쳐주고 잔뜩 중복이 되는 한이 있더라도 프론트 와꾸에 데이터 셋을 맞추는 것이 성능과 생산성 면에서 더 낫더라는 의견이 많이 함양되었기 때문이며 이 이론이 실무에서는 꽤 큰 파장을 불러오긴 했다.
- 과도한 반정규화는 오히려 성능을 저하시킬 수 있다.
	- 이또한 맞는 말이지만 실제로는 과한 정규화가 더 문제되는 경우가 훨씬 많다.
- 반정규화를 위해서는 사전에 데이터의 일관성과 무결성을 우선으로 할지, 데이터베이스의 성능과 단순화를 우선으로 할지를 결정해야 한다.
- 반정규화 방법에는 테이블 통합/분할, 중복 테이블 추가, 중복 속성 추가 등이 있다.
	- 자주 사용되는 방법은 중복 속성 추가가 가장 대표적이고 가장 수정/제거 하기도 편하다.

&emsp;&emsp;

### 테이블 통합

- 두 개의 테이블이 조인되는 경우가 많아 하나의 테이블로 합쳐 사용하는 것이 성능 향상에 도움이 되는 경우 수행한다.
- 두 개의 테이블에서 발생하는 프로세스가 동일하게 자주 처리되는 경우 두 개의 테이블을 이용하여 항상 조회를 수행하는 경우 테이블 통합을 고려한다.

- 테이블 통합의 종류로는 1:1 관계 테이블 통합, 1:N 관계 테이블 통합, 슈퍼타입/서브타입 테이블 통합등이 있다.

#### 테이블 통합시 고려 사항

- 데이터 검색은 좋아지지만 레코드 증가로 인한 처리량이 증가한다.
- 테이블 통합으로 인해 입력, 수정, 삭제 규칙이 복잡해진다.
- Not Null, Default, Check 등의 제약조건 설게가 어려워진다.
- 따라서 이는 갱신보다 조회가 월등히 많은 경우에 수행하는 것이 좋다.

&emsp;&emsp;

### 테이블 분할

- 테이블 분할은 테이블을 수직 또는 수평으로 분할하는 것이다.
	- 주로 파티셔닝이라는 용어로 자주 쓰인다.

#### 테이블 분할 방법 종류

- 수평 분할
	- 설명
		- 레코드를 기준으로 테이블을 분할하는 것
		- 레코드 별로 사용 빈도의 차이가 큰 경우 사용 빈도에 따라 테이블을 분할한다.
- 수직 분할
	- 설명
		- 수직 분할은 하나의 테이블에 속성이 너무 많은 경우 속성을 기준으로 테이블을 분할하는 것이다.
	- 종류
		- 갱신 위주 속성 분할
			- 데이터 갱신시 레코드 잠금으로 인해 다른 작업을 수행할 수 없으므로 갱신이 자주 일어나는 속성들을 수직분할하여 사용한다.
			- 보통 게시글의 경우 게시글 조회수가 갱신이 잦으므로 게시글 내역과, 게시글 메타데이터로 쪼개고 메타데이터에 조회수를 넣으면, 게시글 내역을 다시 수정하는 경우 조회수 갱신으로 게시글 수정이 막히는 경우가 없어진다.
		- 자주 조회되는 속성 분할
			- 테이블에서 자주 조회되는 속성이 극히 일부인 경우, 자주 사용되는 속성들을 수직 분할하여 사용한다.
		- 크기가 큰 속성 분할
			- 이미지나 2GB 이상 저장될 수 있는 텍스트 형식으로된 속성들을 수직 분할하여 사용한다.
			- 보통 게시글의 경우 게시글 내용이 이에 해당된다.
		- 보안을 적용해야 하는 속성 분할
			- 테이블 내의 특정 속성에 대해 보안을 적용할 수 없으므로 보안을 적용해야 하는 속성들을 수직 분할하여 사용한다.
			- 계정 테이블의 비밀번호가 이에 해당된다.

#### 테이블 분할 시 고려 사항

- 기본키의 유일성 관리가 힘들어진다.
- 데이터의 양이 적거나 사용 빈도가 낮은 경우 테이블 분할이 필요한지 고려해야한다.
- 분할된 테이블로 인해 수행 속도가 느려질 수 있다.
- 데이터 검색에 중점을 두어 테이블 분할 여부를 결정해야한다.
	- 이게 제일 중요하다.
		- 왠만한 시스템들은 갱신보단 조회가 9배 이상 많이 실행된다.
		- 국룰 비기능적 요구사항으로 TS 500ms 적는 이유가 이것 때문이다.

&emsp;&emsp;

### 중복 테이블 추가 #아주_가끔_출제 

- 여러 테이블에서 데이터를 추출하여 사용해야하거나 다른 서버에서 저장된 테이블을 이용해야 하는 경우 중복 테이블을 추가하여 작업의 효율성을 증대할 수 있다.

#### 중복 테이블 추가하는 경우

- 정규화로 인해 수행속도가 느려지는 경우
- 많은 범위의 데이터를 자주 처리해야 하는 경우
- 특정 범위의 데이터만 자주 처리해야하는 경우
- 처리 범위를 줄이지 않고는 수행 속도롤 개선할 수 없는 경우

#### 중복 테이블 추가 방법

- 집계 테이블의 추가
	- 집계 데이터를 위한 테이블을 생성하고 각 원본 테이블에 트리거를 설정하여 사용하는 것으로 트리거의 오버헤드를 주의해야한다.
		- 오늘날에는 이것을 해결하기 위해 트리거보단 애플리케이션에서 비동기로 따로 한번 수행시키는 것이 보편적이다.
		- 더 성능을 고려한다면 캐시를 따로 운영해둬서 여기에 쌓아뒀다가 옮기는 것도 방법이긴하다.
			- 다만 이 경우 재난시 사라질 집계라는 점은 유의해야한다
- 진행 테이블의 추가
	- 이력 관리 등의 목적으로 추가하는 테이블
	- 적절한 양의 유지와 활용도를 높이기 위해 기본키를 적절히 설정한다.
		- 보통 배치 작업이나 특정 거래 작업의 이력을 남기기 위한 목적으로 자주 쓰인다.
		- 일부 비동기 작업을 수행하는 경우 (이메일 인증 여부 등) 요긴하게 쓰이는 패턴이다.
- 특정 부분만을 포함하는 테이블의 추가
	- 데이터가 많은 테이블의 특정 부분만을 사용하는 경우 해당 부분만으로 새로운 테이블을 생성한다.
		- 보통 기존 테이블을 기준으로 신규 기능 또는 페이지 등을 개발해야하는 경우 이 방식이 자주 쓰인다.


&emsp;&emsp;

### 중복 속성 추가

- 조인해서 데이터를 처리할 때 자주 사용되는 속성을 하나 더 추가하는 것
- 대표적으로 운송 테이블에 고객번호를 추가하는 것이다.

#### 중복 속성을 추가하는 경우

- 조인이 자주 발생하는 속성인 경우
- 접근 경로가 복잡한 속성인 경우
- 엑세스의 조건으로 자주 사용되는 속성인 경우
- 기본키의 형태가 적절하지 않거나 여러 개의 속성으로 구분된 경우
- 개인적으로 생각할 때는 수정이 쉽기 때문에 가장 실무에서 많이 사용되는 패턴이며 이 다음으로는 파티셔닝, 중복 테이블 추가 순으로 사용된다.

#### 중복 속성 추가시 고려 사항

- 테이블 중복과 속성의 중복을 고려한다.
- 데이터 일관성 및 무결성에 유의해야 한다.
	- 따라서 데이터 갱신 시 추적하여 갱신을 해야하는지에 대한 사용자 정의 제약 조건이 반드시 필요하다.
- SQL 그룹 함수를 이용해 처리 가능해야 한다.
- 저장 공간 낭비가 심해진다.

## 시스템 카탈로그 #매우_자주_출제 


&emsp;&emsp;

### 개념

- 시스템 카탈로그란, 시스템 그 자체에 관련이 있는 다양한 객체에 관한 정보를 포함하는 시스템 데이터베이스
- 시스템 카탈로그 내에 각 테이블은 사용자를 포함하여 DBMS에서 지원하는 모든 데이터 객체에 대한 정의나 명세에 관한 정보를 유지 관리하는 시스템 테이블
- 카탈로그들이 생성되면 데이터 사전에 저장되기 때문에 좁은 의미로는 카탈로그를 데이터 사전이라고도 한다.

&emsp;&emsp;

### 시스템 카탈로그 저장 정보 #매우_자주_출제 

- 시스템 카탈로그에 저장된 정보를 메타 데이터라 함

#### 메타 데이터 유형

- 데이터베이스 객체 정보
	- 테이블, 인덱스, 뷰 등의 구조 및 통계 정보
- 사용자 정보
	- 아이디, 패스워드, 접근 권한 등
- 테이블의 무결성 제약 조건 정보
	- 기본키, 외래키, NULL값 허용 여부 등
- 함수, 프로시저, 트리거 등에 대한 정보

&emsp;&emsp;

### 카탈로그 특징 #매우_자주_출제 

- 사탈로그 자체도 시스템 테이블로 구성되어 일반 이용자도 SQL을 이용해 내용 검색이 가능하다.
	- 물론 대부분 일반 사용자는 막고 관리자만 접근하게 만드는 것이 보편적이다.
- Insert, Delete, Update 문으로 카탈로그 갱신은 허용되지 않는다.
- 데이터베이스 시스템에 따라 상이한 구조를 가진다.
- 카탈로그는 DBMS가 스스로 생성하고 유지한다.

#### 카탈로그의 갱신

- 사용자가 SQL 문을 실행시켜 기본 테이블, 뷰, 인덱스 등에 변화를 주면 시스템이 자동으로 갱신한다.

#### 분산 시스템에서의 카탈로그

- 보통의 릴레이션, 인덱스, 사용자 등의 정보를 포함할 뿐 아니라 위치 투명성 및 중복 투명성을 제공하기 위해 필요한 모든 제어 정보를 가져야 한다.

&emsp;&emsp;

### 카탈로그/데이터 사전을 참조하기 위한 DBMS 내의 모듈 시스템

- 데이터 정의어 번역기
	- DDL을 메타 데이터를 갖는 테이블(카탈로그)로 변화하여 데이터 사전에 저장시킨다.
- 데이터 조작어 번역기
	- 응용 프로그램에 삽입된 DML 문을 주 언어로 표현한 프로시저 호출로 변환하여 질의 처리기와 상호 통신한다.
- Data Directory
	- 데이터 사전에 수록된 데이터를 실제로 접근하는 데 필요한 정보를 관리 유지하는 시스템
	- 시스템 카탈로그는 사용자와 시스템 모두 접근할 수 있지만 데이터 디렉터리는 시스템만 접근 가능하다.
- 질의 최적화기
	- 사용자의 요구를 효율적인 형태로 변환하고 질의를 처리하는 좋은 전략을 모색한다.
- 트랜잭션 처리기
	- 복수의 사용자 환경에서 평행으로 동시에 일어나는 트랜잭션 문제를 해결하여, 각각의 사용자가 데이터베이스 자원을 배타적으로 이용할 수 있도록 한다.
