## 요구사항

&emsp;&emsp;

- 설명
	- 문제 상황
		- 현재 Lit-Tok은 심각하게 책 데이터가 부족함.
			- 특히 리뷰 작성시 이 문제가 대두된다.
		- 책의 데이터를 생각보다 추적하기 쉽지 않다.
		- 추후 스크래핑해 올 리뷰 데이터가 더 가장 중요하다.
			- 지금은 책 데이터를 배치하는 방법을 정리하지만 사실 리뷰 데이터를 스크래핑, 저장하는 것이 더 중요하다.
	- 해결 방법
		- 책 데이터는 추가적으로 베스트셀러 위주로 알라딘에서 수집한다.
			- 그럼에도 불구하고 부족한 책 메타데이터는 리뷰 작성시 도드라지는데 이는 사용자로 하여금 최대한 책 데이터 수량을 감춘다.
				- 예시) 왓챠피디아, StoryGraph
		- 주기적으로 책 데이터를 기준으로 리뷰 데이터를 수집한다.
			- 우선 알라딘 먼저 수집하기로 했다.
	- 나의 선택
		- 리뷰 작성시 사용자의 책 데이터 검색을 돕는 방식을 택했다.
			- 적어도 이렇게 사용하는 것이 사용자에게 덜 불편할 것이라고 생각했다.
		- 알라딘에서 매달 책 데이터와 리뷰 데이터를 수집한다.
			- 알라딘에서 카테고리별 베스트셀러까지 수집하여 리뷰 데이터를 수집하고 있다.

### 스키마 설명

- 메타데이터 스키마를 따로 만든 이유
	- 책 스키마나 리뷰 스키마는 메타데이터 패턴으로 분리해둔 이유는 다음과 같다.
		- count 쿼리를 덜 날리기 위함이다.
			- 이것만 해줘도 조회시 join을 덜하기 때문에 정말 여러모로 도움이 된다.
		- 데이터가 변경되는 시점에 이벤트를 통해 업데이트를 해주고 있다.
			- 예시) 좋아요 추가와 삭제, 댓글 추가와 삭제
		- 이 방식은 데이터가 자주 변경 될 때마다 문제가 생길 가능성이 존재한다.
			- 물론 지금 유저 수가 수십만이 되거나 하는 것도 아니기 때문에 현재 큰 엔지니어링 걱정이 될 정도는 아니긴하다.
			- 걱정이 된다면 캐시에 미리 쌓아뒀다가 1000번 넘기면 업데이트하거나 오버엔지니어링이지만 큐를 추가해던지 하는 해결 방법도 있으니 큰 걱정은 없다.
		- 이 방식의 단점은 상태를 추적하기가 힘들다.
			- 이 데이터와 연관되어 집계 데이터가 업데이트 되는 시점을 추적해야하는게 여간 귀찮은게 아니다.
			- 개발해보니 가장 괜찮았던건 `AggregateRootBaseEntity`를 상속받아서 이곳에서 업데이트를 발생 해주는게 가장 괜찮았다.
				- 솔직히 도메인 문서를 작성해가면서 개발을 해봐도 추적, 관리가 잘 안된다.
					- 특히 이 도메인 문서는 혼자 개발하면서 관리하는게 여간 쉽지가 않았다.
					- 이 문서는  도메인이 여러 개가 붙을 수록 파일이 정말 커져서 보기도 힘들다.
					- 이 문서를 각 도메인 패키지 별로 뜯어서 관리할까 했는데 이러면 문서가 파편화되는 문제가 존재해서 뜯어두지 않았다.
						- 전체적으로 문서를 읽어보면서 비즈니스 로직 흐름 문맥을 꾸준히 이해, 유지하는 것도 꽤 중요하게 느꼈기 때문이다.
				- 여기에서 휴먼 에러가 발생할 것 같다면 ArchUnit 테스트를 하나 추가해주는 것이 가장 괜찮은 방식이지 않을까 조심스레 생각해본다.
					- 나에게 시간이 많았더라면 가장 적극적으로 템플릿 테스트로써 사용했을 테스트 도구가 ArchUnit일 것 같다.

## 구현 과정

&emsp;&emsp;

 
- 순수한 개발 히스토리
	1. 내가 강의에서 보았던 청크기반 구성 먼저 만들어 알라딘 API를 통해 책 데이터 먼저 수집을 했다.
		1. 이 과정에 API 문서와 다른 형태의 데이터가 생각보다 많아서 내가 예상했던 공수가 2배는 더 걸렸다.
	2. 알라딘은 책 데이터와 더불어 계층형 데이터로 카테고리 데이터를 제공해주고 있다. 이를 통해 카테고리 데이터를 먼저 스키마에 저장해둔다.
	3. 카테고리 스키마를 통해 각 카테고리별 추천 책을 수집한다. 이러면 전시용으로 배치할 책 조합을 다양하게 선택할 수 있다.
		1. 물론 이 과정 또한 수월하지 않았다. 카테고리가 중복되는 애들이 꽤 많았던 것으로 기억한다.
	4. 1번과 3번에서 만든 job을 각자 크론잡으로 저장해둔다.
	5. 책 데이터를 기반으로 리뷰 데이터를 수집하기 위해 로컬에 셀레니움 도커를 하나 띄워서 TestContainers를 이용해 연동한다.
	6. 데이터 스크래핑 이전에 IP 차단 방어를 위해 무료 프록시 사이트에서 프록시 사이트에서 프록시 데이터를 파싱한다.
	7. 파싱한 데이터는 프록시 DB에 저장하지 않고 우선 셀레니움을 통해 알라딘 접근 및 조회시 차단 되지 않고 500ms를 유지하는 경우에만 저장한다.
	8. 프록시 풀 테이블이 구성되면 이를 이용해 책 리뷰 데이터를 수집한다.
		1. 이 경우에 셀레니움을 통해 파싱을 하는데 이 과정이 매우 고통스러웠지만 걸린 시간은 일주일정도로 생각보다 빠르게 끝냈다.
	9. 책 리뷰 데이터가 청크 크기 만큼 성공적으로 잘 수집되고 저장되니 속도가 너무 느리다는 문제가 존재해 이를 해결하기 위해 멀티스레드를 도입했고 구현이 가장 단순한 멀티스레드 스탭을 사용했다.
		1. 이 과정중 ItemProcessor에서 프록시 풀을 접근해 리뷰를 스크래핑하는데 큰 문제는 같은 주소를 연속적으로 사용하고 있었고 금방 차단될 수 있으니 이를 방지해야했다.
		2. 비관락을 적용해봤지만 비관락을 적용한 행 이후로 모든 스레드에 락이 걸려서 의미가 없었다. 즉 이 프록시 테이블의 존재가 race 컨디션 자체를 의미한다는 것을 깨달았다.
		3. 그래서 ItemReader로 이 존재를 분산한다는 생각으로 새 Chunk 아이템을 구현했다. 프록시 주소와 책 데이터로 구성된 아이템을 만들고 이를 통해 각 책 아이템별로 다른 프록시 주소를 모든 프록시 풀 테이블 만큼 순차적으로 연속적으로 순회하여 골고루 프록시 주소를 할당했다.
	10. Race 컨디션을 해결했으나 이때는 여러 멀티스레드 방식을 적용해본다고 AsyncItemProcessor & AsyncItemWriter 모델도 적용해보고 파티셔닝 모델도 적용해봤다가 이 파티셔닝 모델 적용 와중이 이 해결책이 떠올라서 이 방식을 고수하게 되었다.

## 느낀점 및 개선 사항

&emsp;&emsp;

- 느낀 점
	- 파티셔닝은 내 방식에서 딱히 유리한 방식은 아니다.
		- 지금 회고를 해보자면 멀티스레드 스텝을 유지하는게 맞는데, 시간이 없어서 롤백을 못했다. 내가 생각하는 파티셔닝을 적용해야하는 사전 조건은 다음과 같다.
		- 파티셔닝을 적용해야하는 사전 조건
			1. 현재 로직에 I/O 인텐시브한 연산 수행 과정이 존재하는 경우 (외부 API Call이 아닌 볼륨 I/O)
			2. 현재 읽어올 모든 아이템에 거칠 프로세스가 거의 일관적으로 비슷한 수행 속도, 연산 Cost인 경우 (읽어올 모든 데이터의 cost가 일정한 경우)
		- 이 두가지 사전 조건이 충족되지 않는 경우이지만 ItemProcess가 과하게 연산을 요구하는 경우에는 멀티스레드를 적용시키는 것이 당연히 좋고 왠만한 경우에는 멀티스레드 스탭으로 해결이 가능하다.
		- 그리고 멀티스레드 스텝을 쓰지 않는 경우 Fallback Policy를 직접 구현해줘야하는 부분들이 있는데 이것을 사실상 포기하고 개발을 하는 것이나 다름이 없어서 좀 과하게 말해서 이것을 쓰지 않으면 스프링 배치를 쓰는 이유가 딱히 없다.
		- 나는 이 미리 구현해둔 Fallback Policy를 굳이 안쓰고 직접 구현하여 생산성을 크게 잃어버렸다.
		- 가능만 하다면 이 쓸오버 엔지니어링 덩어리를 롤백하고 싶다.
	- 셀레니움은 정말 실패를 많이 한다.
		- 이 원인을 알고 싶어도 제대로 원인을 사람이 없다.
		- 그나마 내가 직접 해결한 원인은 공유메모리 문제의 경우가 다이고 간헐적으로 발생하는 예외는 원인을 알 수가 없다.
			- 스택오버플로우를 찾아보면 직접 여러번 돌려준다고 이야기를 하던데 좀 듣고서 허망했다.
			- 어떤 이는 PlayWright로 갈아 타시기도 하던데 이 분의 경우에는 e2e 테스트 도구로 쓰시던 분이라 내 경우에 맞는지는 잘 모르겠다.
	- 책 데이터가 쌓일 수록 더 많은 메모리가 필요하다.
		- 이 문제는 내가 취업하고나면 서버용 컴퓨터를 하나 장만해서 배치만 따로 내 로컬에서 돌려줘볼까 한다.
			- 차단 문제가 있을 수도 있기야 하겠지만 말이다.
	- 생각보다 파싱은 구현이 쉽다.
	-
