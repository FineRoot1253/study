## 소프트 파싱 VS 하드 파싱

&emsp;&emsp;

- 설명
	- SGA, System Global Area
		- 설명
			- 서버 프로세스와 백그라운드 프로세스가 공통적으로 액세스하는 데이터와 제어 구조를 캐싱하는 메모리 공간
		- 구성 요소
			- DB Buffer Cashe
			- Redo Log Buffer
			- Shared Pool
				- Library Cache
					- SQLs
				- Data Dictionary Cache
	- 라이브러리 캐시
		- SQL 파싱, 최적화, 로우 소스 생성 과정을 거쳐 내부 프로시저를 반복 재사용할 수 있도록 캐싱해 두는 메모리 공간
		- SGA의 구성요소 중 하나
		- DBMS는 사용자가 전달한 SQL을 라이브러리 캐시에서 먼저 존재하는지 찾아본다.
			- 캐시에서 바로 찾으면 실행 단계, 못찾으면 최적화 단계를 거친다.
			- **바로 찾는 것을 소프트 파싱**, **최적화 -> 로우 소스 생성 과정을 하드 파싱**이라고 부른다.

&emsp;&emsp;

### SQL 최적화 과정이 하드한 이유

- 설명
	- 옵티마이저가 최적화에 사용하는 정보
		- 기본 정보
			- 테이블, 컬럼, 인덱스 구조
		- 오브젝트 통계
			- 테이블 통계, 인덱스 통계, 컬럼 통계
		-  시스템 통계
			- CPU 속도, Single Block IO 속도 Multiblock IO 속도
		- 기타
			- 옵티마이저 관련 파라미터
	- 위의 모든 정보를 활용해 계산하는 작업으로, DB에서 몇 안되는 CPU Inbound 작업이 SQL 최적화 작업이다. 
		- 라이브러리 캐시가 필요한 이유이며 SQL 최적화 과정이 하드하다고 부르는 이유이다.

### 이름없는 SQL 문제

&emsp;&emsp;

- 이름에 대한 설명
	- 사용자 정의 함수/프로시저, 트리거, 패키지 특징 
		- 생성할 때부터 이름을 갖는다.
		- 컴파일한 상태로 딕셔너리에 저장되며 사용자가 삭제하지 않는 한 영구 보관된다.
		- 실행할 때 라이브러리 캐시에 적재해 여러 사용자가 공유하면서 재사용한다.
	- SQL 특징
		- 따로 이름이 없으며 전체 SQL 텍스트가 이름 역할을 한다.
			- 딕셔너리에 저장하지도 않는다.
		- 처음 실행할 때 최적화 과정을 거쳐 동적으로 생성한 내부 프로시저를 라이브러리 캐시에 적재함으로써 여러 사용자가 공유하면서 재사용한다.
		- 캐시 공간이 부족하면 버려졌다가 다음에 다시 실행할 때 똑같은 최적화 과정을 거쳐 캐시에 적재한다.
	- 오라클, SQL Server가 SQL을 영구 저장하지 않는 이유
		- IBM DB2의 경우에는 영구 저장이 가능하지만 다른 벤더들은 그렇지 않다.
			- 오라클 10g에 SQL ID라는 SQL 텍스트와 1:1 대응되는 ID도 있지만 SQL 텍스트가 변경되면 SQL ID도 변경된다.
		- DBMS에서 수행되는 SQL이 모두 완성된 SQL이 아니고 수정될 가능성이 높고 일회성으로 사용되는 SQL도 많다.
		- SQL을 이것 저것 저장하면 이를 찾는데에도 시간이 걸리니 아예 영구 저장하지 않도록 선택했다.

### 공유 가능 SQL

&emsp;&emsp;

- 설명
	- 유저를 단순히 한번 조회하는 조회 쿼리를 만들었다고 가정한다.
	- 만약 500만 유저 중 20%가 한번에 로그인을 시도하는 이벤트가 발생한다고 가정하면, SQL 문은 그 자체로 모두 다른 SQL이므로 100만 유저에 해당하는 하드 파싱이 발생된다.
