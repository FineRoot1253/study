# 데이터 저장 구조 및 I/O 메커니즘

&emsp;&emsp;

## SQL이 느린 이유

&emsp;&emsp;

-  설명
	- IO
		- OS 또는 IO 서브시스템이 디스크에서 데이터를 찾는 작업
		- 이 처리시간 동안 프로세스는 잠을 잔다.
		- 대부분 IO를 이야기 할 때는 디스크 IO를 의미한다.
	- 프로세스
		- 실행 중인 프로그램
		- 생성, 준비, 실행, 대기, 종료 등의 상태로 구성된 생명주기를 가진다.
		- 생명주기
			- 생성
				- 프로세스가 생성된 상태
			- 준비
				- 실행되기 위해 대기 중인 상태
				- 실행 상태로 넘어가는 것을 디스터럽트라고 부른다.
			- 실행
				- 프로세스가 실행되는 상태
				- 준비 상태로 넘어가는 것을 인터럽트라고 부른다.
				- 대기 상태로 넘어가는 경우는 이벤트 대기나 IO 요청의 경우이다.
			- 대기
				- 실행 중이던 프로세스가 중지된 상태
				- IO 또는 이벤트가 완료되면 준비 상태로 넘어간다.
				- 즉, 인터럽트 없이 잘 실행되던 프로세스도 IO가 발생되면 프로세스가 중지된다.
				- CPU 사용권을 OS에 반환하고 잠시 수면 상태에서 IO가 완료되기를 대기한다.
				- 정해진 OS 함수를 호출(IO Call)하고 CPU를 반환한 채 알람을 설정하고 대기 큐(Wait Queue)에서 잠을 자는 것이다.
				- 즉, IO가 많으면 프로세스는 느려진다.
				- 평균 IO Call 속도는 평균 10ms이고 초당 100 블럭쯤 읽는다.
					- 큰 캐시를 가진 SAN 스토리지는 4 ~ 8ms 쯤 된다.
					- 최근 SSD를 활용하는 스토리지는 1 ~ 2ms 쯤 된다.
				- 허나 어떤 SQL이 Singblock IO로 10000블록을 읽기 시도 한다면 SSD도 10초 이상 대기한다.
				- 수많은 프로세스에 의해 동시다발적으로 발생하는 IO Call 때문에 디스크 경합이 심해지고 그만큼 대기 시간도 늘어난다.
					- 10초가 아닌 20 ~ 30초도 가능하다는 이야기

## 데이터베이스 저장 구조

&emsp;&emsp;

- 설명
	- 테이블스페이스
		- 설명
			- 세그먼트를 담는 컨테이너
			- 여러 개의 데이터파일(디스크 상의 물리적인 OS 파일)로 구성됨
			- 테이블 생성시 세그먼트를 생성한다
		- 구성 요소
			- 데이터파일 (물리적인 OS 파일시스템 상의 파일)
				- 세그먼트 (테이블, 인덱스, 파티션, LOB)
					- 익스텐트
						- 블록
							- 로우
	- 세그먼트
		- 설명
			- 테이블, 인덱스처럼 데이터 저장공간이 필요한 오브젝트
			- 테이블, 인덱스를 생성할 때 데이터를 어떤 테이블스페이스에 저장할지를 지정한다.
			- 파티션 구조가 아니라면 테이블도 하나의 세그먼트이며 인덱스도 하나의 세그먼트이다.
			- LOB 컬럼은그 자체가 하나의 세그먼트를 구성하므로 자신이 속한 테이블과 다른 별도 공간에값을 저장한다.
		- 구성 요소
			- 익스텐트 여러 개
	- 익스텐트
		- 설명
			- 공간을 확장하는 단위, 연속된 블록들의 집합
			- 테이블이나 인덱스에 데이터 입력을 하다가 공간이 부족하면 해당 오브젝트가 테이블스페이스로부터 추가로 할당받는다.
			- 모든 익스텐트가 같은 파일에 존재하지 않은 경우도 많다.
				- 보통 서로 다른 파일에 위치한 경우가 많다.
			- 하나의 테이블 스페이스를 여러 데이터파일로 구성하면 파일 경합을 줄이기 위해 DBMS가 데이터를 가능한 여러 데이터파일로 분산해 저장하기 때문이다.
			- ==**익스텐트 내 블록은 서로 인접한 연속된 공간이지만 익스텐트끼리는 연속된 공간이 아니다.**==
		- 구성 요소
			- 블록 여러 개
	- 블록
		- 설명
			- 사용자가 입력한 레코드를 실제로 저장하는 공간, 데이터를 읽고 쓰는 단위
			- DB2, SQL Server와 같은 벤더사는 페이지라는 용어를 사용한다. (이게 좀 더 학과에서 많이 사용된다.)
			- 한 블록은 하나의 테이블이 독점한다.
				- 한 블록에 저장된 레코드는 모두 같은 테이블 레코드라는 뜻이다.
				- 다만 다중 테이블 클러스터인 경우에는 한 블록에 여러 테이블 레코드 저장이 가능하다.

&emsp;&emsp;

### DBA, Data Block Address

&emsp;&emsp;

- 설명
	- 모든 데이터 블록은 ==**디스크 상에서 몇 번 데이터파일의 몇 번째 블록**==인지 나타내는 고유 본인 주소 값을 가지며 이를 DBA라고 부른다.
	- ROWID
		- ==**DBA + 로우 번호로 구성**==되므로 이를 분해하면 읽어야 할 테이블 레코드가 저장된 DBA를 알 수 있다.
		- **인덱스를 이용해 테이블 레코드를 조회할 때는 인덱스 ROWID를 이용**한다. 
		- ROWID는 
	- **테이블 스캔시 테이블 세그먼트 헤더에 저장된 익스텐트 맵을 이용**한다.
		- 익스텐트 맵을 통해 각 익스텐트의 첫 번째 블록 DBA를 알 수 있다.
		- 연속된 블럭의 나열이기 때문에 이를 기준으로 연속해서 저장된 블록일 읽으면 원하는 블록을 찾을 수 있다.
			- 보편적인 배열 개념이나 다름 없다.

## 블록 단위 IO

&emsp;&emsp;

- 설명
	- 오라클은 일반적으로 8kb 크기의 블록을 사용하므로 1byte를 읽기 위해 8kb를 읽어들인다.
		- `SELECT value FROM V$parameter WHERE name = 'db_block_size';`
		- 위 명령으로 뷰를 볼 수 있다.
		- 2kb, 4kb, 8kb, 16kb 크기 블록도 가능하며 OS에 따라 다르며 MS SQL Server는 8kb만 지원 하는 것이 특징이다.
		- **테이블만 아니라 인덱스 또한 이 블록 단위로 데이터를 읽고 쓴다.**

## 시퀀셜 액세스 vs 랜덤 액세스

&emsp;&emsp;

- 시퀀셜 엑세스
	- 논리적 또는 물리적으로 연결된 순서에 따라 차례대로 블록을 읽는 방식
	- 인덱스 리프 블록은 앞뒤를 가리키는 주소값을 통해 논리적으로 서로 연결돼 있다.
		- 이 주소 값에 따라 앞 또는 뒤로 순차적으로 스캔하는 방식 (B+tree)
		- **기본적으로 블록끼리 논리적 연결고리는 없다.**
	- 오라클은 세그먼트에 할당된 **익스텐트 목록을 세그먼트 헤더에 맵(map)**으로 관리한다.
		- 각 익스텐트의 첫 번째 블록 주소를 알고 있으므로 이를 이를 연속적으로 읽어들이는 것이며 이를 Full Table Scan이라고 부른다. 
- 랜덤 액세스
	- 물리적인 순서를 따르지 않고 레코드 하나를 읽기 위해 한 블록씩 접근(touch)하는 방식

## 논리적 IO vs 물리적 IO

&emsp;&emsp;

### DB 버퍼 캐시

&emsp;&emsp;

- 설명
	- 라이브러리 캐시
		- 실행 코드를 저장해두는 '코드 캐시'
	- DB 버퍼 캐시
		- 블록들을 저장해두는 데이터 캐시
		- 어렵게 읽은 데이터를 미리 캐싱하여 반복적인 IO Call을 줄여준다.
	- 서버 프로세스와 데이터파일 사이에 버퍼캐시가 있으므로 데이터 블록을 읽을 땐 항상 버퍼캐시부터 탐색한다.
	- 운 좋게 캐시에서 블록을 찾는다면 바쁜 시간에 프로세스가 잠을 자지 않아도 되니 좋다.
		- 잠을 딱 한 번만 자면, 다음에는 자지 않아도 된다.
		- 거기다 공유 메모리영역(SGA)이므로 다른 프로세스에서도 성능 이득을 본다.
	- `show sga`명령을 통해 `V$SGA$`뷰 확인이 가능하며 이곳에서 각 캐시별 크기 확인이 가능하다.

&emsp;&emsp;

### 논리적 IO vs 물리적 IO

&emsp;&emsp;

- 설명
	- 논리적 블록 IO
		- SQL을 처리하는 과정 중 발생한 총 블록 IO
		- 논리적으로 메모리에서 읽어낸 일량을 의미한다.
		- 메모리를 경유하지 않는 Direct Path IO를 고려하면 논리적 IO는 메모리 IO와 Direct Path IO를 더한 개념이다.
			- Direct Path IO는 디스크 소트 과정에서 소트 Runs로부터 블록을 읽거나 병렬 쿼리로 Full Scan을 수행할 때 Direct Path Read 방식을 사용한다.
		- 일반적으로 메모리 IO를 논리적 IO로 볼 수 있다.
			- 메모리상의 버퍼 캐시를 경유하기 때문이다.
	- 물리적 블록 IO
		- 디스크에서 발생한 총 블록 IO를 말한다.
		- SQL 처리 도중 읽어야 할 블록 버퍼캐시에서 찾지 못하는 경우에만 논리적 블록 IO 중 일부를 물리적으로 IO한다.
		- 메모리 IO는 전기적 신호이지만 물리적 IO는 액세스 암 (Arm)을 통해 물리적 작용이 일어나므로 당연히 논리적 IO에 비해 훨씬 느리다.
		- 거기에 디스크 경합이 발생하는 경우 더 느리다.
		- 실제 SQL 실행때마다 다르다.
			- 논리적 횟수는 일정하게 같아도 DB 버퍼의 점유율로 인해 점점 일량이 줄어든다.

&emsp;&emsp;

### 블록 IO의 적절량

&emsp;&emsp;

- 설명
	- 아무리 최적화해도 절대적인 업무 환경에 따라 블록 IO의 발생량은 천차만별이다.
	- 검색 범위, 조인 테이블 수, 대상 테이블 크기, 인덱스 구조 등에 의해 결정된다.

&emsp;&emsp;

### 버퍼 캐시 히트율

&emsp;&emsp;

```
BCHR = (캐시에서 곧바로 찾은 블록 수 / 총 읽은 블록 수) * 100
     = ((논리적 IO -  물리적 IO) / 논리적 IO) * 100
     = (1 - (물리적 IO) / (논리적 IO)) * 100
```

- 설명
	- 위의 수식은 버퍼 캐시 효율 검산을 위해 사용되던 전통적 지표이다.
		- 전통적으로 BCHR은 읽은 전체 블록 중에서 물리적인 디스크 IO를 수반하지 않고 곧바로 메모리에서 찾은 비율을 나타낸다.
	- 애플리케이션 특성에 따라 다르지만 통상적인 온라인 트랜잭션을 주로 처리하는 애플리케이션이면 시스템 레벨에서 평균 히트율 99%를 달성해야한다.
		- 핵심 트랜잭션이 시스템 전체 부하를 대부분 차지하므로 열심히 튜닝하면 달성하기 어렵지 않다.
- 핵심 포인트
	- 물리적 IO가 성능 결정을 하긴 하지만 더 중요한 것은 ==**논리적 IO가 줄어들어야 한다.**==
		- 계산해보면 논리적 IO는 늘 일정하지만 물리적 IO는 비결정적이라 ==**통제 가능한 변수는 논리적 IO**==이기 때문이다.
		- 이를테면, BCHR이 70%, 논리적 IO가 10000이라면, 물리적 IO는 3000개 쯤 발생한다.
			- 이때, 논리적 IO를 1000개로 줄이면 물리적 IO는 300으로 감소하고 성능이 10배 상승한다.
	- ==**논리적 IO를 줄이는 방법은 읽는 총 블록 개수를 줄이는 것이다.**==
	- SQL 트레이스로 Call 수집 통계 정보에서 Query와 Current 항목을 더한 값이 논리적 IO이다.
		- 즉 SQL 수행 과정에 읽은 총 블록 개수이다.
		- DISK 항목은 디스크에서 물리적으로 읽은 블록 개수이다.
		- 이때 논리적 IO를 Disk와 Query를 더하는 사람도 있는데 그건 옳은 계산은 아니다.
			- DB 버퍼 캐시에서 읽은 블록에는 디스크에서 읽은 블록이 이미 포함되어있기 때문
	- 위의 공식에 따르면 다음과 같다.
		- `BCHR = (1 - (Disk / (Query + Current))) * 100`
		- 하지만 이것이 높다고 해서 항상 효율적인 SQL을 의미하지 않는다.
		- 인덱스와 NL 조인을 학습하게 되면 알게 된다.
- 결론
	- ==**논리적 IO를 줄여 발생 가능한 물리적 IO를 줄이는 것이 SQL 튜닝 핵심이다.**==

## Single Block IO vs Multiblock IO

&emsp;&emsp;

- Single Block IO
	- 설명
		- 캐시에서 찾지 못한 블록을 디스크에서 읽어들일 때 한 번에 한 블록씩 요청하는 방식
	- 특징
		- 소량의 데이터 블록을 읽어들일 때 주로 사용된다.
		- 기본적으로 인덱스 이용 시 인덱스와 테이블 모두 Single Block IO를 사용한다.
	- 사용하는 경우
		- 인덱스 루트 블록을 읽을 때
		- 인덱스 루트 블록에서 얻은 주소 정보로 브랜치 블록을 읽을 때
		- 인덱스 브랜치 블록에서 얻은 주소 정보로 리프 블록을 읽을 때
		- 인덱스 리프 블록에서 얻은 주소 정보로 테이블 블록을 읽을 때
- Multiblock IO
	- 설명
		- 캐시에서 찾지 못한 블록을 디스크에서 읽어들일 때 한 번에 여러 블록씩 요청하는 방식
	- 특징
		- 대량 데이터 블록을 읽어 들일 때 효율적이다.
		- 테이블 전체 스캔시 주로 사용된다.
		- 테이블이 클수록 Multiblock IO 단위도 커야 좋다.
			- 프로세스 잠자는 횟수를 줄여준다.
			- 즉 대용량 Full Scan이 예상되는 배치 작업등에는 Multiblock IO를 크게 만들어주면 성능이 대폭 좋아진다.
		- 정확히는 인접한 블록들을 한꺼번에 읽어 캐시에 미리 적재하는 기능이다.
			- 같은 익스텐트에 속한 블록을 의미하며 이 경계를 뛰어넘지는 못한다.
			- 익스텐트에 속한 블록을 다 읽고나서 바로 다음 익스텐트를 찾지는 않는다.
				- 일단 버퍼 캐시에 저장하고나서 그 다음 다음 익스텐트를 찾는다.
		- DBMS 블록 사이즈가 얼마건 간에 OS 단에서는 보통 1MB 단위로 IO를 수행한다. (OS마다 다르긴하다.)
		- `SHOW parameter db_file_multiblock_read_count` 명령으로 검색 해볼 수 있다.
			- `ALTER session SET db_file_multiblock_read_count = 128;` ALTER 명령을 통해 변경 가능하다.
		- 어차피 읽어 들이는건 OS라 많이 설정해도 OS의 IO 단위 만큼 읽는다.

&emsp;&emsp;

### Multiblock IO 중간에 발생하는 Single Block IO

&emsp;&emsp;

- 설명
	- 읽어야 할 여러 블록 중 캐시 버퍼 체인에 없다고 가정할 때, 중간에 못찾은 연속적 블록은 Multiblock으로 읽지만 익스텐트의 마지막 블록같은 경우에는 Single Block으로 IO Call을 한다.
	- Full Scan 중에 Chain이 발생한 로우를 읽을 때도 Single Block IO 방식으로 디스크 블록을 읽는다.

## Table Full Scan vs Index Range Scan

&emsp;&emsp;

- 설명
	- Tabe Full Scan
		- 설명
			- 테이블 전체를 스캔해서 읽는 방식
	- Index Range Scan
		- 설명
			- 인덱스를 이용해서 읽는 방식
			- 대부분 인덱스를 이용한 테이블 액세스라고 부른다.
			- 인덱스에서 일정량을 스캔하면서 얻은 ROWID로 테이블 레코드를 찾아가는 방식
			- 대부분 이 방식으로 유도한다.
				- 허나 인덱스가 조회 성능을 떨구는 경우도 허다하다.
				- 집계용 SQL과 배치 프로그램이 특히 그렇다.
					- 이 프로그램에서 사용되는 SQL은 온라인 SQL보다 튜닝하기 쉽다.
					- 이 경우 Table Full Scan으로 유도하면 빨라진다.
					- 조인이 포함되었다면 해시 조인으로 유도해주면 된다.
			- 주로 랜덤 액에서와 Single Block IO 방식으로 디스크를 읽는다.
			- ==**캐시에서 블록을 못 찾으면, 레코드 하나를 찾기 위해 계속 잠을 자는 방식이다.**==
			- 많은 데이터를 읽어들일 때는 Table Full Scan 보다 불리하다.
		- 주의점
			- 적은 데이터를 읽어 들일 때는 각 블록을 단 한 번 읽는 Table Full Scan보다 불리하다.

- 필자는 인덱스로 테이블을 액세스하는데 일정 카디널리티 량을 넘어서는 경우 경고 표시를 놓는 기능이 있어야 한다고 주장한다.

## 캐시 탐색 메커니즘

&emsp;&emsp;

- 설명
	- 특징
		- 해시 알고리즘을 통해 버퍼 헤더를 찾고 거기서 얻은 포인터로 버퍼 블록을 액세스 하는 방식을 사용한다.
	- 해시 구조 특징
		- 같은 입력 값은 항상 동일한 해시 체인 (= 버킷)에 연결된다.
		- 다른 입력 값이 동일한 해시 체인에 연결되기도 한다.
		- 해시 체인 내에서는 정렬이 보장되지 않는다.
	- 메모리 버퍼 캐시 탐색 과정이 진행되는 경우
		- 인덱스 루트 블록을 읽을 때
		- 인덱스 루트 블록에서 얻은 주소 정보로 브랜치 블록을 읽을 때
		- 인덱스 브랜치 블록에서 얻은 주소 정보로 리프 블록을 읽을 때
		- 인덱스 리프 블록에서 얻은 주소 정보로 테이블 블록을 읽을 때
		- 테이블 블록을 Full Scan 할 때

### 메모리 공유 자원에 대한 액세스 직렬화

&emsp;&emsp;

- 설명
	- 캐시 버퍼는 SGA 영역이므로 엄연히 다른 프로세스와 블록 정합성 문제를 야기할 수 있다.
		- 따라서 한번에 한 프로세스만 접근하게 만드는 직렬화가 필요하다.
		- 이런 줄서기 구조를 만드는 매커니즘이 래치(Latch)이다.

&emsp;&emsp;

#### 캐시버퍼 체인 래치

&emsp;&emsp;

- 설명
	- 대량의 데이터를 읽을 때 모든 블록에 대해 해시 체인을 탐색한다.
	- 이 동안 다른 프로세스가 체인 구조를 변경하면 곤란하므로 해시 체인 래치가 존재한다.
	- 체인 앞 단계에 키를 가진 프로세스만이 체인들에 접근 가능하게 만들어져 있다.
	- SGA를 구성하는 서브 캐시마다 별도의 래치가 존재한다.
		- 버퍼캐시의 경우
			- 캐시버퍼 체인 래치
			- 캐시버퍼 LRU 체인 래치
	- 버퍼캐시 히트율이 빠른 성능을 표현한다지만 캐시 IO가 래치 경합 때문에 생각만큼 빠르지 않을 수 있다.
		- 거기다가 버퍼 블록 자체에도 직렬화 매커니즘이 존재하며 이것이 버퍼 LOCK이다.
	- 결론
		- 캐시 경합을 줄일려면 SQL 튜닝을 통해 쿼리의 작업량(논리적 IO) 자체를 줄여야한다.

&emsp;&emsp;

#### 버퍼 Lock

&emsp;&emsp;

- 설명
	- 오라클은 보통 버퍼 Lock을 사용한다. 
		- 다 읽었다고 판단한 블록을 찾아 해제 했는데 이 사이에 다른 프로세스가 접근하여 데이터를 읽고 쓴다면 정합성 문제가 발생하기 때문이다.
		- 먼저 버퍼 Lock을 설정해 버퍼 블록 자체에 대한 직렬화 문제를 해결한 것이다.
